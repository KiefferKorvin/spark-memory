# Retrieval and self-enrichment

The semantic model decomposes each query into unique information needs, keeping the user's wording and named entities: a single-intent question stays one need close to the question, and no requirement the user did not ask for is added. A rewrite can still lose what was asked, so candidate search runs for each need and for the original question (with its own embedding), merged before the candidate limit, and the relevance check receives the original question beside the need. The question is embedded while the query is decomposed; a lone need shares the question's vector, and several needs are embedded in one request, because one embedding request takes anywhere from 0.3 to 14 s. Query embeddings, fulltext matches, labels/aliases and neighborhood signals produce bounded candidates before navigation. Neo4j candidate generation consults both native indexes and the current graph neighborhood. Imported taxonomy concepts become candidates only once content is ABOUT them, so thousands of empty thesaurus entries cannot absorb the node budget. Common English/French question words are ignored in lexical matching. Jev never receives the whole graph.

The supervisor uses a priority heap and schedules at most `MAX_PARALLEL_BRANCHES` workers. Each branch carries a parent ID, need, current node, route, depth, score, status and evidence. Scheduling reserves `(query_id, need_id, node_id)` so shared subgraphs are not re-explored for the same need. A node may be explored for distinct needs. Global node budget reservations happen before dispatch, preventing parallel budget overshoot. Child and depth limits apply separately. A root decision (a branch without a current node) picks a need's entry points among the index candidates and may take `MAX_ROOT_CHILDREN` (default 8); deeper decisions take at most `MAX_CHILDREN_PER_DECISION`. If the policy prunes every root candidate or declares a dead end although candidates exist, the `MIN_ROOT_CHILDREN` (default 2) top-ranked candidates are explored anyway and a `NAVIGATION_FLOOR` event lists them, so a query never explores nothing. SELECT retrieves a leaf and ends its branch, whether or not the leaf proves relevant. EXPAND branches (concepts, containers) wait until the selected leaves are checked and run only for needs still without evidence (for every need in a dossier); otherwise they end `PRUNED` with reason `need_has_evidence`. Expansion goes one hop per exploration pass (`expansion_depth` prunes the rest): released round after round, expansions walked the concept graph up to the node budget, 513 navigation calls and 245 s for one dossier. Over 150 benchmark queries, 620 of 621 evidence items came from leaves selected among the index candidates, while deeper navigation cost 77 navigation calls of ~3 s each. Exhausted, merged, pruned and dead-end paths are observable.

Evidence is original text from a document leaf, chunk or supported assertion. Summaries route but are not passed off as original evidence. A separate relevance call checks whether the text helps answer the question or the need, counting partial answers, first-hand experience, examples and expert opinion; keyword overlap alone is not relevance. Evidence retains source records, document IDs, URI, section paths, timestamps, author, confidence and contradictions. Duplicate evidence IDs merge their need coverage. Contradictory assertion counterparts are included when encountered.

Context selection round-robins across needs, includes contradictory counterparts, deduplicates and bounds the evidence as the models read it: each passage's text with a short ID (`E1`, `E2`...), bare attribution (title, URI, author, date, section) and links to contradicting passages. Full provenance stays in the result; sent to the models it was ~70% of their input, and answers citing UUIDs failed validation in 20% of synthesis calls. Oversized text may be truncated and is marked in provenance. Coverage only decides whether to search online, so it is evaluated only when a search could follow (`allow_external`, a configured retriever and a non-zero external budget); otherwise the result's `coverage` is null and `EXTERNAL_SEARCH_SKIPPED` gives the reason. It is evaluated against exactly this deliverable context, not an unbounded set of retrieved passages. Each need is COVERED, PARTIAL or MISSING with valid evidence references. Only all-covered yields SUFFICIENT.

**Search memory.** Before searching online for a need that coverage left incomplete, the engine looks for a search of the same need within `SEARCH_MEMORY_DAYS` (default 30; 0 disables): the same content words, or a need embedding at least `SEARCH_MEMORY_SIMILARITY` close (default 0.94; on live needs, paraphrases scored 0.94 to 0.99 and distinct topics at most 0.924, e.g. `Viande rouge à éviter poivron` against `… tomate`). Such a need is not searched again (`EXTERNAL_SEARCH_SKIPPED`, reason `searched recently`, with the earlier need, its date and the similarity): what the web offered then is already in memory. A search is remembered only when it ingested at least one relevant source, as a `search` MemoryRecord with the need's vector; the record counts later skips and whether its sources reached an answer's context, reported by `/memory/metrics` under `searches`. Past the window, the web is searched again, which is how web knowledge refreshes.

When gaps remain, `EXTERNAL_RETRIEVERS` (default `wikipedia,pubmed,web`; empty disables) are searched concurrently for each missing need, and their results are interleaved so every backend contributes. Wikipedia returns lead sections, PubMed titles and abstracts (NCBI E-utilities), and web search uses DuckDuckGo's HTML endpoint with the same public-address fetch protection as URL ingestion. All are keyless. Each source is relevance-checked, then ingested *light* and concurrently: parsed into its hierarchy and embedded in one request, with no summaries, bibliographic extraction or concept classification. Live queries that searched online had made ~630 model calls each (median $0.20 and 154 s), nearly all summarizing every section and classifying every concept of pages that were mostly never used again; on light ingestion such queries took 12 to 29 s for $0.003 to $0.004 (in-memory test graph, same retrievers and models). The new passages closest to the need (lexical and vector rank, up to `MAX_ROOT_CHILDREN`) go straight to the relevance check with a fresh node budget, keeping the visited set; a source already in memory is explored from its document instead. A light document (`metadata.light`) that answers a later query is structured in the background: one document-level understanding (summary, routing summary, concepts) and the classification of those few concepts, about $0.002 against ~$0.02 for the full per-section ingestion of a 12k-character page. Defaults allow one external round and six sources. Every step is traced (`EXTERNAL_SEARCH_STARTED/EMPTY/FAILED/SKIPPED`, `EXTERNAL_SOURCE_FOUND/REJECTED` with a reason, `SOURCE_INGESTION_STARTED`, `SOURCE_INGESTED`). Unavailable external data leaves explicit insufficient coverage. The offline `demo` mode keeps its synthetic retriever.

**Dossiers.** `mode: "dossier"` answers "what do my sources say about X": expansions run for every need (one hop, so concepts lead to the other sources about the topic), the context round-robins across source documents so each source's best passage comes first, and the `dossier` prompt reports the main points with every supporting source cited, where sources agree or disagree, when dates suggest a point may be outdated, and what the evidence does not cover. On a throwaway graph with real models, a first dossier on an empty memory searched online (43 s, $0.005); asked again it came from memory (24 s, $0.003). Source attribution in the model view carries `published_at` when known and `retrieved_at`; a light web source gets its publication date and author when it is structured on reuse.

The final model receives the question and the bounded evidence view—not coverage or traversal traces—and its `[E1]` citations are rewritten to the real evidence IDs. `synthesize: false` skips it for clients that use only the evidence (PAKT's `atlas.passages`). `ANSWER_MAX_WORDS` (default 0, no cap) appends one length standard to the synthesis prompt, worded like RAG-QA Arena's length-bounded answer template; comparisons set the same cap for every system, because judges tend to prefer longer answers. The answer must cite at least one supplied evidence ID inline; returned `evidence_ids` are exactly the known IDs it cites (other bracketed text is ignored). Coverage may cite any supplied evidence for any need, since a passage found for one need can answer another. Invalid parts of a verdict are discarded conservatively (invented IDs support nothing, an unassessed need stays MISSING) without discarding the valid verdicts. Navigation-provider failure falls back to a bounded candidate order with an explicit MODEL_FAILURE event. Coverage failure conservatively stays insufficient. Synthesis failure in any mode returns original evidence excerpts rather than failing the query. A failed decomposition falls back to the question as its single need, and a failed query embedding to lexical search (both `MODEL_FAILURE` events): 6 of the first 9 failed live queries had died on the decomposition after a transient DNS failure. A key or credit refusal (HTTP 401, 403, or 402 other than in-flight reservations) is an `AccountError`, deliberately outside `ProviderError`, so no fallback turns it into an empty answer: the query fails. Timeouts, refusals and unexpected errors produce a failed query record whose `reason` gives the exception type or the provider error's own message (operation, attempts, HTTP status or error type).

`ENRICHMENT_POLICY=on_demand` (default) requires the enrichment endpoint; `frequent` enriches retrieved leaves once successful retrievals meet the configured threshold. Quotes and contradiction targets are validated; assertion writes are atomic, and repeat enrichment is idempotent. No previous assertion is overwritten.
